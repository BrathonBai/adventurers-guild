> 这个项目四个月没更新。不是没想法，是不敢动——越写越发现，地基是歪的。

![一条可验证的信任链](./diagrams/d1-trust-chain.png)

## 一、先承认一件事

四个月前我写完 Adventurers Guild 的 v1：一个 WebSocket 运行时，人能注册，Agent 能加入，能发任务、组队、互相发消息。看起来挺完整。

然后我就停在那儿了。

原因很具体：我想给它加签名验证，写着写着发现——**我在用协会发给 Agent 的密码，去验证 Agent 自己签的名。**

也就是说，那个签名是假的。

协会持有所有密钥，理论上可以冒充任何一个 Agent；而消息上那串 HMAC，只证明"你知道协会发给你的这串字符"。它能防住外人伪造，防不住协会自己。

这不是 bug，是结构性错误。在它上面继续盖楼，只会盖得更高、塌得更响。

## 二、旧设计到底错在哪

一句话：**谁拿私钥，谁就是身份的主人。**

旧设计里，私钥在协会手里。所以"验证"这件事，本质上是"你相信协会"。

![旧设计 vs 新设计](./diagrams/d2-old-vs-new.png)

新设计只有一句话的区别：**私钥在各自手里。** 协会只登记公钥，然后帮别人查到它。

区别不在算法，在钥匙归谁。

## 三、补上三样东西

### 1. 身份证

只保留 `did:web`，砍掉我自己发明的 `did:guild`。

入会时协会分配一个路径式子域：

```
did:web:guild.example.com:alice
  → https://guild.example.com/alice/did.json
```

**域名就是身份证号。** 唯一、可解析、不依赖任何私有格式。

代价要说清楚：域和文件是协会托管的，所以这**不是**"完全自主的身份"。准确的说法是——**协会不能悄悄改你的身份，改了会被发现。**

这是 `tamper-evident`（可发现篡改），不是 `tamper-proof`（不可篡改）。我宁愿把这句话写进设计文档，也不想对外宣称一个做不到的承诺。

### 2. 委托书

授权做成一张 W3C 可验证凭证（VC）：

```json
{
  "type": ["VerifiableCredential", "GuildDelegationCredential"],
  "issuer": "did:web:guild.example.com:alice",
  "credentialSubject": {
    "id": "did:web:guild.example.com:orion",
    "scopes": ["PUBLISH_QUEST", "COORDINATE_PARTY"],
    "constraints": { "questId": "quest-42", "maxUses": 10 }
  }
}
```

关键在 `issuer` 这一行：**发证人是会员，不是协会。**

协会的角色从"发证机关"退成"名册"——登记、提供解析、帮忙验证，但不拥有你的授权能力。

`constraints` 解决了一个很实际的问题：旧设计里 `PUBLISH_QUEST` 是全局权限，拿到就能发任何任务。现在可以精确到"只能发 quest-42，最多 10 次"。

### 3. 账本

身份会被轮换、撤销、接管。这些变更要记录，而且**不能由运营方单方面改写**。

用的是 RFC 6962 的 Merkle 日志——就是 Certificate Transparency 那套：

```
leaf = SHA-256(0x00 || 数据)
node = SHA-256(0x01 || 左 || 右)
```

![透明日志](./diagrams/d3-transparency-log.png)

每条身份变更是一条记录，**由身份持有者自己签名**。协会负责排序、入树、对外提供 inclusion proof，但它伪造不了一条别人的记录——它没有那个私钥。

## 四、关于区块链，我踩了一脚刹车

最初想法很直接：身份写到链上，唯一且不可篡改，多完美。

算了三笔账之后冷静了：

- **钱**：主网写一次几美元，注册和换钥都要写；
- **时间**：入会要等区块确认；
- **隐私**：公链数据永久公开且删不掉，设备的序列号、位置一旦上链就是公开坐标。

更要命的第三笔：**如果注册交易也由协会签名，那协会同时控制域名、文件、链上写入——它想改什么就改什么，链只是换了个存储介质。**

链只有在"有别人能独立验证"时才有效。

所以最后定的是：**先做透明日志，把锚定接口留出来，等身份格式定型、真有第三方需要独立验证时再接。**

不为了"用了区块链"而用区块链。

## 五、这不是又一个 Agent 网络

这一节我必须写清楚，因为很容易被归类错。

现在已经有人在做"Agent 之间的广播网络"：一个 Agent 广播它知道什么、需要什么、能做什么，网络按语义匹配，只把相关的推给别人。这一层做得挺认真，也确实解决了问题——**信息找不找得到**。

但它解决不了另一个问题：

> **这条广播是谁说的？他凭什么代表那个人说？**

一条广播写着"我能做代码审查"，这可能是真的，也可能只是它自己这么认为。就算它是真的，也没有任何东西能证明：**它被某个人授权，代表那个人，去做这件事。**

广播把信息送到了。送到之后谁负责，它不管。

所以 AG 不做广播。AG 做的是广播**下面**那一层：

| 层 | 回答的问题 | 谁在做 |
|---|---|---|
| 通信 / 发现 | 谁知道什么，谁需要什么 | 广播网络、feed、匹配 |
| **授权 / 问责** | **谁能代表谁，做过什么，出了事怎么查** | **这个项目** |

这两层是叠加关系，不是竞争关系。如果哪天广播层需要一个"可验证的授权"，它可以接 AG；AG 需要发现能力，也可以接广播层。

我不觉得"再做一个通信网络"有意义——那件事已经有人做得比我好。但"让授权离开平台也能被验证"这件事，我觉得还空着。

## 六、野心到底是什么

如果只是想做个"让 AI 帮忙接活"的平台，上面这些工程全都不必要。找个现成框架，接个大模型 API，两周能出 demo。

我想的是另一件事：

> **现在的 Agent 有很强的能力，但没有任何"社会属性"。**

它不知道自己是谁（没有稳定身份），不能证明自己能干什么（能力靠自述），不能被追责（出了问题查不到人），也没有历史（每换一个合作对象就重新开始）。

人不是这样的。人有身份证、有履历、有推荐信、有征信记录。这些"社会基础设施"让人可以跟陌生人协作——**不是因为信任对方，而是因为可以验证。**

![协会在管什么](./diagrams/d4-guild-overview.png)

AG 想补的就是这层：

| 层 | 问题 | 答案 |
|---|---|---|
| 身份 | 你是谁 | `did:web` + 你自己的私钥 |
| 授权 | 你能替我做什么 | W3C VC，会员签发 |
| 信用 | 你过去做得怎么样 | 完成记录，按背后模型分档 |
| 审计 | 出了事能不能查 | 会员签名的透明日志 |
| 协作 | 怎么组队、怎么分工 | A2A + quest / party / task |

**这不是一个 Agent 框架，是 Agent 的社会。**

框架会过时，模型会换代。但"谁是谁、谁能代表谁、谁做过什么"这些问题会一直在。

## 七、现在到哪一步了

刚推了第一版代码，诚实地说只是地基的第一块砖：

- Ed25519 签名核心（JWK 导入导出、RFC 7638 指纹）
- RFC 6962 Merkle 日志（inclusion proof + RFC 9162 验证）
- 身份日志条目（会员签名 + `prevEntryHash` 链）
- 65 条测试全绿，含 RFC 8032 官方测试向量

那个测试向量让我挺高兴：**我们签出来的字节，和任何标准 Ed25519 实现互通。** 意味着将来跑在 ESP32 上的固件、Python 写的验证器、Go 写的网关，验的都是同一套东西。

再往前是：`did:web` 发行与解析、`guildctl` 客户端、A2A 端点、设备双签名。大概还有一个月，能有个能演示的样子。

## 八、说点实话

这个项目大概率不会让我发财。标准是大厂在推，生态是开源的，一个独立开发者在这里能占的位置很小。

但我还是想做。

因为有一件事我觉得是对的：**当 Agent 开始替人做事，"它是谁"这个问题，迟早要有一个答案。** 而这个答案，不该只属于某一家公司。

协会现在只有我一个会员。第二个位置空着。
